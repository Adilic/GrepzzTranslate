# 第二册：怎样组织、维护和迁移一个项目

## 第 1 章：项目变大时，文件怎样分工

### 1.1 并不是每个程序都要几十个目录

一个把几行文本改成另一种格式的一次性脚本，可以从两个文件开始：

```text
small-task/
├─ convert.py
└─ README.md
```

只用标准库，就不用安装第三方包；README 仍应说明 Python 版本、输入、运行方法和输出位置。

以后需要复用、测试或交给别人时，再拆模块和打包。

### 1.2 一个中小型可安装项目

```text
textstats-kit/
├─ pyproject.toml       项目元数据、依赖和构建规则
├─ README.md            使用方法
├─ .gitignore           版本管理排除规则
├─ src/
│  └─ textstats_kit/
│     ├─ __init__.py
│     ├─ __main__.py    python -m textstats_kit 的入口
│     ├─ cli.py         命令行参数和输出
│     ├─ core.py        可以独立测试的业务逻辑
│     └─ data/          随包发布的小型只读资源
└─ tests/
   └─ test_core.py
```

cli.py 负责接收命令和显示结果；core.py 负责计算。这样，测试计算时不必真的打开终端，以后增加图形界面也能继续使用同一个计算函数。

这只是一个起点。网站、数据分析、机器学习项目会增加各自需要的文件夹。判断结构是否合适，先看能否说清每个文件负责什么、输入从哪里来、结果到哪里去。

### 1.3 源码直接放根目录，还是放进 src

包文件夹直接放项目根目录，叫 flat layout；再套一层 src，叫 src layout。本示例选择后者，需要先安装项目再运行。

使用 src 时，Python 不容易仅仅因为“恰好在项目目录”就找到源码。漏了安装步骤，更容易发现；安装包漏文件仍需另外测试。[布局比较](https://packaging.python.org/en/latest/discussions/src-layout-vs-flat-layout/)

### 1.4 可编辑安装与普通安装

`pip install -e .` 中，`.` 是当前项目，`-e` 表示“可编辑安装”：环境使用你正在编辑的源码。普通 `pip install .` 或安装 wheel，通常会把构建好的文件装入环境，形成单独的一份。

可编辑安装后，改普通 Python 代码，重启程序通常就能看到结果。若改的是项目名称、命令入口或需要编译的组件，还可能要重新安装或构建。

普通安装后，修改工作区里的源码不会自动改掉环境中的副本。想知道运行的是哪一份，查看模块的 `__file__` 路径。

## 第 2 章：读懂 pyproject.toml

pyproject.toml 是项目的说明和配置文件。先阅读下面例子，不必新建文件；第三册附带的教学项目已经有一份。

```toml
[build-system]
requires = ["setuptools>=75"]
build-backend = "setuptools.build_meta"

[project]
name = "textstats-kit"
version = "0.1.0"
description = "A small text statistics teaching project"
requires-python = ">=3.12"
dependencies = []

[project.optional-dependencies]
dev = ["pytest>=8,<10", "build>=1,<2"]

[project.scripts]
textstats = "textstats_kit.cli:main"

[tool.setuptools.packages.find]
where = ["src"]

[tool.setuptools.package-data]
textstats_kit = ["data/*.txt"]
```

### 2.1 构建部分

`build-system` 说明“用什么工具制作安装包”。本例用 setuptools。`requires` 列出制作时需要的工具，`build-backend` 指定实际负责制作的工具入口。

`python -m build` 发起制作，setuptools 按配置完成制作。前者叫“构建前端”，后者叫“构建后端”。先记住谁发起、谁制作即可。

### 2.2 项目元数据与运行依赖

`name` 是安装包的名字；`version` 是这个项目的版本；`requires-python` 是支持的 Python 版本；`dependencies` 是运行程序还需要安装哪些包。这些项目说明叫“元数据”。

Python 版本要求不代表系统要求；只支持 Windows 等限制也应写清并测试。

### 2.3 开发依赖与可选依赖

`optional-dependencies` 把额外需要的包分组。本例的 `dev` 组包括测试和打包工具。执行 `pip install -e ".[dev]"`，会同时安装当前项目和这组工具。

这种可选组也叫 extras。它只往当前环境多装一些包，不会创建另一个环境。dev 是我们起的组名，可以由项目决定。

### 2.4 命令行入口

`textstats_kit.cli:main` 的意思是：运行 textstats_kit 包中 cli.py 的 main 函数。安装项目后，就能通过生成的 `textstats` 命令调用它。

改命令映射后通常要重装；可编辑安装下只改函数代码，通常重启即可。

### 2.5 tool 配置

`tool` 下的设置由指定工具读取。例如 `tool.setuptools` 是给 setuptools 看的，不是让 Python 直接执行的代码。

data/*.txt 指定要打包的文本文件。源码中有，不等于安装包中也有，要安装后检查。

字段定义与更多构建后端示例可查 [pyproject.toml 官方指南](https://packaging.python.org/en/latest/guides/writing-pyproject-toml/)。

## 第 3 章：源码、配置、输入、资源和输出分开

### 3.1 五类文件为何要区别对待

| 类别 | 变化来源 | 通常怎样保存 |
| --- | --- | --- |
| 源码 | 开发者修改 | Git |
| 默认配置 | 项目定义 | Git 中的示例或默认值 |
| 部署／个人配置 | 每个环境不同 | 环境变量或本地配置 |
| 输入与资源 | 用户输入、模型、固定模板 | 明确路径或资源管理 |
| 输出、日志与缓存 | 程序产生 | 可写目录，不混入安装文件 |

目录可以合放，但要分清用途：用户数据库不能当缓存删除。

### 3.2 程序安装目录不一定能写

开发目录能写，不代表安装到系统目录后还能写。

让用户指定输出目录，或选用用户数据目录；不要写死某个人的桌面路径。

### 3.3 包内小资源的读取

```python
from importlib.resources import files

text = files("textstats_kit").joinpath("data", "example.txt").read_text(
    encoding="utf-8"
)
```

上面的代码在安装好示例项目后使用：它找的是包里的 example.txt，所以换一个工作目录也能读到。若某个库必须接收真实文件路径，可用 `importlib.resources.as_file` 临时提供路径，并在它的使用范围内完成读取。

大型模型、数据集和私人数据库通常另行准备。文档应说明去哪获取、用哪个版本、放在哪里、怎样检查文件是否完整。

### 3.4 配置的优先级必须明确

如果同一个设置写了多处，程序必须决定听谁的。例如：命令行参数优先，其次环境变量，再其次配置文件，最后才用代码默认值。选哪种规则都要写清并照着实现。

读到的设置往往只是文字，还要检查含义。例如 `bool("false")` 得到 True，因为它只检查字符串是否为空，不会理解英文 false。数字设置也要检查能否转成数字、是否在允许范围内。

### 3.5 秘密与普通配置

API 密钥、数据库密码不应写进源码或提交到 Git。`.env.example` 可列出变量名与空占位，实际 .env 放本地并被忽略。

环境变量也可能泄露；日志中不要打印密码、带密码的链接或全部环境变量。正式服务可使用专门的密钥管理工具。

### 3.6 文本、编码和换行

读写文本时明确编码，例如 UTF-8。不同系统的默认值可能不同。

测试中文和空格路径，并保持文件名大小写一致；Windows 上能找到的文件，Linux 上未必能找到。

## 第 4 章：记下依赖，让下一次安装有据可依

### 4.1 直接依赖和传递依赖

假设你要装 A，而 A 需要 B，B 又需要 C。A 是你的直接依赖，B、C 是间接带进来的依赖。如果只记录 A，下次安装时 B、C 的版本可能变了。

pip 会寻找一组能同时满足这些要求的版本，这一步叫“依赖解析”。安装冲突可能发生在 B、C 身上，所以要看错误里具体是哪两个要求不能同时满足。

### 4.2 范围、固定版本、锁定与哈希

| 手段 | 能解决什么 | 不能保证什么 |
| --- | --- | --- |
| 版本范围，如 >=1,<2 | 允许安装哪些版本 | 每次安装到同一版本 |
| 固定版本，如 ==1.4 | 选定某个版本 | 每个平台都能安装它 |
| 锁文件 | 记下选好的直接、间接依赖等信息 | 驱动、系统和外部服务也相同 |
| 文件哈希，即文件的校验值 | 检查下载文件是否与记录相符 | 程序一定正确或没有漏洞 |

锁文件要配合相应工具使用。只把文件命名为 lock，不会让 pip 自动按它安装；跨系统时，也要确认工具是否支持那种用法。

### 4.3 应用和库的依赖策略不同

如果是自己运行的应用，通常希望每次装出同一套版本。如果是给别人使用的库，则要留出兼容范围，否则容易与对方已有的包冲突。

库开发者仍可以固定自己的测试环境，或用多套版本测试。“我测试了什么”和“允许用户安装什么”是两件事。

### 4.4 requirements 与 constraints

requirements 回答“要装哪些包”；constraints 回答“如果要装某个包，它的版本不能超出什么范围”。只写进 constraints，不会让那个包自动被安装。

例如 constraints.txt 中限制 `some-dependency<3`，只有这次安装确实需要它时，限制才起作用。不要把 constraints 当成另一份完整安装清单。

### 4.5 pip freeze 不是需求设计器

`pip freeze` 列出当前环境中已安装的包和版本。它不知道哪些是项目需要的，哪些只是你昨天试着装过的。

因此，先确认这个环境只装了该项目需要的内容，再保存清单。还要检查清单中有没有第一台电脑的路径或可编辑安装记录；这些内容直接搬过去可能失效。需要时再使用专门的锁定工具。

### 4.6 真正有价值的复现记录

至少记录：

1. 源码提交号。
2. Python 实现、版本和平台架构。
3. 依赖声明及确切安装结果／锁文件。
4. 模型、静态资源和数据库结构版本。
5. 配置变量名与默认值，不包含秘密。
6. 系统组件、外部服务及验证步骤。

“我的电脑上 pip list 一样”只是其中一层。pip 官方对固定版本、哈希校验与离线发行文件集合有更具体说明：[可重复安装](https://pip.pypa.io/en/stable/topics/repeatable-installs/)。

## 第 5 章：测试与日志让迁移可验证

### 5.1 测试不是只有一个按钮

| 层次 | 问题 | 文本统计工具中的例子 |
| --- | --- | --- |
| 单元测试 | 小段逻辑是否正确 | 空文本应统计为零行零词 |
| 集成测试 | 多组件协作是否正常 | 读取 UTF-8 文件并生成结果 |
| 安装冒烟测试 | 新环境能否启动 | 安装 wheel 后执行 --demo |
| 端到端验收 | 用户流程是否完成 | 指定输入，产生符合约定的 JSON |

测试应检查真实问题，不必机械地重复代码实现。

### 5.2 测试代码应方便脱离界面运行

把函数写成接受输入、返回结果，而不是每次自己弹窗口、读固定路径。例如 `summarize(text)` 比“在函数内部永远读取我的桌面文件”更容易测试。

测试应自己准备小文件和临时目录，用完再清理。测试中共用的准备步骤常叫“夹具”。不要依赖桌面上碰巧存在的文件，也不要改真实用户数据。

### 5.3 为什么源码测试通过还要测试安装包

测试在源码目录运行时，可能无意中读到了本地资源；wheel 却漏打包了这些资源。也可能依赖某个未声明但开发环境已安装的包。

因此应至少用第二个干净环境安装构建产物，并从源码目录之外运行一次。第三册会实际做这个实验。

### 5.4 日志要回答发生了什么

日志记录时间、执行步骤和错误，不记录密码或整份私人输入。

持续记录程序情况时，通常用 Python 的 logging 工具。命令行工具应把结果和报错分开输出，否则其他程序读取 JSON 结果时，可能被混入的报错文字打断。

报错后显示的一串文件名和行号，叫“栈追踪”。最后一行说明错了什么，上面的行说明从哪里一步步运行到这里。先找到自己代码对应的文件和行号。

## 第 6 章：Git、协作与环境更新

### 6.1 Git 不等于文件夹同步软件

Git 保存你选择并提交的文件版本，不会把整个电脑搬走。没有跟踪的文件、被忽略的文件，都需要另行决定如何迁移。

典型 .gitignore 可以包括：

```gitignore
.venv/
__pycache__/
*.py[cod]
*.egg-info/
.pytest_cache/
build/
dist/
.env
.env.*
!.env.example
```

数据库、模型和输出目录是否忽略取决于项目。小型非敏感测试数据可能应该提交，不能机械排除所有 data 文件夹。

### 6.2 四种改变意味着四种后续操作

| Git 更新了什么 | 通常还需做什么 |
| --- | --- |
| 普通源码 | 重启相关进程并测试 |
| 依赖／入口元数据 | 重新安装或同步环境 |
| 模型或资源清单 | 下载／校验对应资源 |
| 数据库结构 | 按项目迁移步骤升级结构并备份 |

pull 本身不会自动完成这些事情，除非项目另有明确自动化。

### 6.3 分支与双机接力

两台电脑也可能改到同一处。尽量在 A 改完后提交、推送，再到 B 拉取后继续。必须同时改不同功能时，可以各用一个分支，最后合并。

遇到冲突，先决定保留哪些修改，再合并、测试、提交；不要直接清掉未提交的工作。

### 6.4 Git 不是个人数据备份的唯一答案

代码丢了可以从 Git 取回；私人数据库、大模型和用户文件，可能根本没进 Git。它们需要另设存放位置和备份办法，不能因代码已上传就认为全部保存好了。

Git LFS 可管理大文件，但有安装和额度等条件，不必把所有生成文件都放进 Git。

## 第 7 章：构建产物、部署与迁移

### 7.1 三种交付方式

| 方式 | 接收者需要什么 | 典型场景 |
| --- | --- | --- |
| 源码与环境配方 | 对应 Python、依赖和资源 | 继续开发、研究复现 |
| wheel | 兼容 Python 与运行依赖 | 安装库或 Python 应用 |
| 独立应用／容器镜像 | 对应系统或容器运行条件 | 桌面用户、服务部署 |

wheel 需要 Python 才能安装使用，不是双击运行的 Windows exe。用 PyInstaller 打包，也通常要按目标系统分别制作。容器能统一部分系统环境，但 CPU 类型、GPU、网络和数据保存位置仍要核对。

### 7.2 同系统迁移步骤

以两台 Windows x64 电脑为例：

1. 确认源项目的提交、依赖清单、资源说明已保存。
2. B 安装适合项目的 Python 和 Git。
3. B 克隆源码，在自己的路径创建 .venv。
4. 按项目文档安装依赖和项目本身。
5. 配置所需环境变量、系统组件、数据与模型。
6. 运行检查、测试和一条真实用户流程。
7. 记录结果，之后按更新类型维护环境。

### 7.3 跨系统迁移多了什么

跨系统还要查路径、大小写、权限、启动命令、系统功能和需编译的组件。

一个使用 Windows 专属 OCR 的项目，即使业务代码是 Python，也不是只重建 .venv 就能在 Linux 使用。要替换平台能力或明确只支持 Windows。

### 7.4 离线安装需要准备的集合

在与目标兼容的平台上准备依赖 wheel、自己的 wheel、Python 安装来源、资源文件及系统组件来源。若下载集合中含源码包，还要处理构建依赖；仅缓存几个主包不够。

下面是离线安装的两步示意，不是要求现在执行。先有核对过的 requirements.txt：第一条在有网的准备电脑下载；把清单和 wheelhouse 文件夹带到目标电脑，再执行第二条。两边都要选对 Python。

```powershell
python -m pip download --only-binary=:all: -r requirements.txt -d wheelhouse
python -m pip install --no-index --find-links=wheelhouse -r requirements.txt
```

这不自动包括模型、数据库、驱动或远端服务。目标平台不同，默认下载的 wheel 也可能不适合；跨平台下载需要明确目标参数并在真实目标验收。

### 7.5 部署不是只有安装

安装完成后，还要按用途安排运行：网站服务要决定如何启动、记录日志、重启和备份；桌面程序要找到资源和可写目录；定时任务要设置运行账号、起始目录和失败通知。

## 第 8 章：这些工具分别帮什么忙

| 工具类别 | 解决的主要问题 | 初学阶段怎样看 |
| --- | --- | --- |
| venv | 项目环境隔离 | 先掌握其机制 |
| pip | Python 包安装 | 先掌握目标环境与依赖 |
| Python 版本管理器 | 安装／选择不同解释器 | 多版本项目时再引入 |
| uv、Poetry 等项目工具 | 整合环境、依赖解析与锁定等流程 | 遵守仓库已选方案，不混用锁文件 |
| Conda 类环境管理 | 管理 Python 及较多非 Python 组件 | 科学计算等场景按项目要求使用 |
| pipx 类工具 | 隔离安装独立命令行应用 | 不等于给当前项目安装依赖 |
| Docker 等容器工具 | 封装一部分运行系统环境 | 部署需求明确后学习 |
| 编辑器 | 编辑、调试和导航 | 解释器选择仍需核对 |

不必把表中的工具都装上。先遵守项目已有方案，避免多个工具同时改同一环境。

## 第 9 章：拿到陌生项目的通用阅读顺序

1. 先看 README 的用途、支持系统、运行入口和外部服务。
2. 找 pyproject.toml、requirements、锁文件、environment.yml 或容器配置，确定它采用的方案。
3. 看配置示例，分清必填设置与秘密。
4. 看 tests 和示例输入，了解预期行为。
5. 找命令入口或主程序，顺着核心流程读。
6. 在独立环境安装，先跑最小示例，再跑完整功能。
7. 记录实际 Python 路径、资源位置和验证结果。

## 第二册检查题

1. 为什么源码目录可运行，不等于 wheel 可运行？
2. 应用为什么常固定环境，而给别人安装的库通常要表达兼容范围？
3. requirements 中列出一个包，与 constraints 中列出同一个包，有什么区别？
4. requirements 完全一致，还可能有哪些环境差异？
5. 为什么更新依赖的提交不能只 pull 后继续运行旧进程？
6. 若程序只在当前编辑器中正常，换目录就失败，应优先检查什么？

答案见[第三册](03-labs-and-troubleshooting.md)。这套思考方式比记住某个框架的安装命令更能复用。
