## 第 1 章：项目结构应该服务于规模

### 1.1 并不是每个程序都要几十个目录

一个把几行文本改成另一种格式的一次性脚本，可以从两个文件开始：

```text
small-task/
├─ convert.py
└─ README.md
```

只使用标准库时，没有第三方依赖需要安装，但仍要说明 Python 版本、输入格式、运行方法和输出位置。不是没有 requirements.txt 就不规范。

脚本开始反复使用、被其他程序导入、增加测试或需要交付时，再考虑拆分模块与打包。

### 1.2 一个中小型可安装项目

```text
textstats-kit/
├─ pyproject.toml       项目元数据、依赖和构建规则
├─ README.md            使用方法
├─ .gitignore           版本管理排除规则
├─ src/
│  └─ textstats_kit/
│     ├─ __init__.py
│     ├─ __main__.py    python -m textstats_kit 的入口
│     ├─ cli.py         命令行参数和输出
│     ├─ core.py        可以独立测试的业务逻辑
│     └─ data/          随包发布的小型只读资源
└─ tests/
   └─ test_core.py
```

命令行层负责“怎样和用户交互”，核心层负责“给定输入怎样得到结果”。分开后，可以不模拟终端就测试业务函数，也可以以后增加图形界面而复用核心逻辑。

这不是所有项目必须遵守的唯一模板。Web 应用会增加路由、服务和数据库层；数据分析可能增加 notebooks；机器学习可能增加训练配置与模型管理。共同原则是明确职责和数据流。

### 1.3 flat layout 与 src layout

flat layout 把包直接放在根目录，简单直观；src layout 多一层 src，通常先安装项目再运行。

src 的一个作用，是减少根目录中的源码被“碰巧导入”，更容易暴露项目没有正确安装、发布包漏文件等问题。代价是新手要理解可编辑安装。[布局比较](https://packaging.python.org/en/latest/discussions/src-layout-vs-flat-layout/)

不要为了通过测试，让 tests 随意把多个目录追加到 sys.path；那可能只让源码目录可用，掩盖真实安装后的缺陷。

### 1.4 可编辑安装与普通安装

`pip install -e .` 适合开发，让环境关联到工作区代码。普通 `pip install .` 或安装 wheel 则通常在环境中安装构建后的文件。

可编辑安装后修改普通 Python 源码通常不必再次安装，但修改入口配置、包元数据或原生扩展可能需要重新安装或构建。

普通安装后，你改工作区源码，环境里的副本不会自动跟着变。要问“当前 import 的 __file__ 指向哪里”，不能仅凭自己打开了哪个文件来判断。

## 第 2 章：读懂 pyproject.toml

下面是一份教学项目的基本配置，具体可运行版本位于附带示例目录：

```toml
[build-system]
requires = ["setuptools>=75"]
build-backend = "setuptools.build_meta"

[project]
name = "textstats-kit"
version = "0.1.0"
description = "A small text statistics teaching project"
requires-python = ">=3.12"
dependencies = []

[project.optional-dependencies]
dev = ["pytest>=8,<10", "build>=1,<2"]

[project.scripts]
textstats = "textstats_kit.cli:main"

[tool.setuptools.packages.find]
where = ["src"]

[tool.setuptools.package-data]
textstats_kit = ["data/*.txt"]
```

### 2.1 构建部分

build-system 告诉构建前端应该准备什么后端。这里使用 setuptools；也有其他后端，不要求同时学习。

`python -m build` 是调用构建前端；后端负责按照项目规则生成 wheel 等产物。构建工具和你的业务程序是不同角色。

### 2.2 项目元数据与运行依赖

name 是发行包名；version 是项目自身版本，不是 Python 版本。requires-python 描述兼容的解释器范围；dependencies 描述运行时第三方包需求。

如果代码确实只支持某个平台，也需要在文档、依赖标记和测试中体现，不能只因为配置写着 Python >=3.12 就认为跨平台成立。

### 2.3 开发依赖与可选依赖

optional-dependencies 可以定义命名分组。本示例的 dev 是开发用测试和构建工具，`pip install -e '.[dev]'` 同时安装项目与这一组依赖。

extras 不创建第二个虚拟环境，只是在同一环境增加指定依赖。组名 dev 是项目约定，不是 Python 的保留词。

### 2.4 命令行入口

`textstats_kit.cli:main` 表示到 cli 模块找到 main 函数。安装器据此生成 textstats 命令入口。

新增或修改命令映射后通常要重新安装项目；只改 main 函数体，在可编辑安装中重启程序即可观察。

### 2.5 tool 配置

tool 区域供特定工具读取，例如 setuptools、pytest 或格式检查器；Python 解释器不会自动执行所有 tool 配置。

这里明确把 data/*.txt 包含进发行包。源码目录有文件，不代表构建产物自动含有它。必须用安装后测试证明。

字段定义与更多构建后端示例可查 [pyproject.toml 官方指南](https://packaging.python.org/en/latest/guides/writing-pyproject-toml/)。

## 第 3 章：源码、配置、输入、资源和输出分开

### 3.1 五类文件为何要区别对待

| 类别 | 变化来源 | 通常怎样保存 |
| --- | --- | --- |
| 源码 | 开发者修改 | Git |
| 默认配置 | 项目定义 | Git 中的示例或默认值 |
| 部署／个人配置 | 每个环境不同 | 环境变量或本地配置 |
| 输入与资源 | 用户输入、模型、固定模板 | 明确路径或资源管理 |
| 输出、日志与缓存 | 程序产生 | 可写目录，不混入安装文件 |

小项目可以把部分目录放一起，但必须知道它们各自是什么。不能把用户数据库当作可随时删除的构建缓存。

### 3.2 程序安装目录不一定能写

开发时项目在自己的桌面，写源码旁边很方便。安装到系统目录、容器或只读文件系统后，这个假设可能不成立。

通用程序应明确接受输出目录，或选用合适的用户数据目录。运行参数中指定输入输出的位置，比硬编码 `C:\Users\某人` 更可迁移。

### 3.3 包内小资源的读取

```python
from importlib.resources import files

text = files("textstats_kit").joinpath("data", "example.txt").read_text(
    encoding="utf-8"
)
```

这样表达的是“读取这个已安装包的资源”，不依赖终端工作目录。对需要真实文件路径的第三方库，可研究 importlib.resources.as_file 的上下文管理；不要假设资源永远是源码目录里的普通路径。

模型、巨型数据集、私人数据库通常不应直接塞进普通 wheel。应记录资源版本、下载来源、校验方式与存放位置，让部署过程能独立准备。

### 3.4 配置的优先级必须明确

一个合理但并非唯一的规则是：命令行参数高于环境变量，高于配置文件，高于代码默认值。重要的是实现和文档一致。

读取字符串后还要转换并校验：`"false"` 本身是非空字符串，`bool("false")` 为 True，不能用它随便解析布尔配置。端口号、超时、路径也要做类型和范围检查。

### 3.5 秘密与普通配置

API 密钥、数据库密码不应写进源码或提交到 Git。`.env.example` 可列出变量名与空占位，实际 .env 放本地并被忽略。

环境变量也不是绝对安全的保险柜；不要把完整进程环境、带密码的 URL 或凭据打印进日志。生产环境可能使用专门的秘密管理服务，那是更进一步的部署主题。

### 3.6 文本、编码和换行

读写文本应有明确编码，例如 UTF-8。Windows 的本地默认编码与其他平台可能不同；“中文乱码”未必是字体问题。

路径中有中文或空格应作为正常情况测试。对文件名大小写也保持一致：部分文件系统区分大小写，Windows 上碰巧能导入 `Utils` 不代表 Linux 上能导入 `utils`。

## 第 4 章：依赖配方与可复现环境

### 4.1 直接依赖和传递依赖

假设应用依赖 A，A 又依赖 B，B 依赖 C。只写 A 的允许范围，下一次安装时 B、C 可能变化。

依赖解析器是在约束条件下选择一组版本，不是简单照着列表依次下载。冲突可能来自间接依赖，必须看完整错误链。

### 4.2 范围、固定版本、锁定与哈希

| 手段 | 能解决什么 | 不能保证什么 |
| --- | --- | --- |
| 版本范围 | 表达兼容边界 | 每次得到同样结果 |
| 固定版本 | 指定包版本 | 下载文件一定相同、所有平台都支持 |
| 完整解析结果／锁文件 | 记录依赖选择及相关信息 | 系统库、驱动、外部服务完全一致 |
| 文件哈希 | 校验发行文件是否与记录一致 | 业务正确、软件没有漏洞 |

不同工具的锁文件格式和跨平台语义不同。不能因为文件名叫 lock 就假设所有工具会自动使用。

### 4.3 应用和库的依赖策略不同

一个由你直接部署的应用，通常希望环境版本明确、可重现。一个给其他开发者安装的库，则需要在元数据中表达兼容范围，过度把所有依赖锁死可能与使用者环境冲突。

库仍可以在自己的测试环境使用锁定版本，或者测试多组版本；“发行给别人时允许范围”和“自己测试时记录确切版本”并不矛盾。

### 4.4 requirements 与 constraints

requirements 指定要安装的需求；constraints 限制解析时可选的版本，不会仅因为被列在那里就自动要求安装该包。

例如 constraints.txt 中限制 `some-dependency<3`，只有这次安装确实需要它时，限制才起作用。不要把 constraints 当成另一份完整安装清单。

### 4.5 pip freeze 不是需求设计器

freeze 记录当前环境中看见的安装状态，不知道哪些包是你临时试验的，也不理解哪些是业务直接依赖。

只应从用途明确、状态清楚的环境生成记录，并检查本机路径、可编辑条目和无关包。更成熟的项目可使用依赖编译或锁定工具，但不应跳过对依赖关系的理解。

### 4.6 真正有价值的复现记录

至少记录：

1. 源码提交号。
2. Python 实现、版本和平台架构。
3. 依赖声明及确切安装结果／锁文件。
4. 模型、静态资源和数据库结构版本。
5. 配置变量名与默认值，不包含秘密。
6. 系统组件、外部服务及验证步骤。

“我的电脑上 pip list 一样”只是其中一层。pip 官方对固定版本、哈希校验与离线发行文件集合有更具体说明：[可重复安装](https://pip.pypa.io/en/stable/topics/repeatable-installs/)。

## 第 5 章：测试与日志让迁移可验证

### 5.1 测试不是只有一个按钮

| 层次 | 问题 | 文本统计工具中的例子 |
| --- | --- | --- |
| 单元测试 | 小段逻辑是否正确 | 空文本应统计为零行零词 |
| 集成测试 | 多组件协作是否正常 | 读取 UTF-8 文件并生成结果 |
| 安装冒烟测试 | 新环境能否启动 | 安装 wheel 后执行 --demo |
| 端到端验收 | 用户流程是否完成 | 指定输入，产生符合约定的 JSON |

不是所有改动都需要庞大测试集；关键是覆盖真实风险，不要只写与实现一模一样的断言。

### 5.2 测试代码应方便脱离界面运行

把函数写成接受输入、返回结果，而不是每次自己弹窗口、读固定路径。例如 `summarize(text)` 比“在函数内部永远读取我的桌面文件”更容易测试。

测试通常应使用临时目录或测试夹具，不写真实用户数据，不依赖你电脑中恰好存在的文件。

### 5.3 为什么源码测试通过还要测试安装包

测试在源码目录运行时，可能无意中读到了本地资源；wheel 却漏打包了这些资源。也可能依赖某个未声明但开发环境已安装的包。

因此应至少用第二个干净环境安装构建产物，并从源码目录之外运行一次。第三册会实际做这个实验。

### 5.4 日志要回答发生了什么

日志适合记录时间、阶段、错误类型和必要上下文，不适合无条件输出密码或整份私人输入。

通常用 logging，而不是到处散落 print；命令行工具的业务结果和诊断信息应区分输出渠道，避免错误信息破坏下游 JSON 解析。

栈追踪最后一行给出异常，上方路径和调用顺序帮助定位；先找自己代码中触发异常的位置，再判断是否底层依赖有问题。

## 第 6 章：Git、协作与环境更新

### 6.1 Git 不等于文件夹同步软件

Git 记录你明确提交的文件版本。未跟踪文件、本机环境、秘密和大型生成物应有各自管理策略。

典型 .gitignore 可以包括：

```gitignore
.venv/
__pycache__/
*.py[cod]
*.egg-info/
.pytest_cache/
build/
dist/
.env
.env.*
!.env.example
```

数据库、模型和输出目录是否忽略取决于项目。小型非敏感测试数据可能应该提交，不能机械排除所有 data 文件夹。

### 6.2 四种改变意味着四种后续操作

| Git 更新了什么 | 通常还需做什么 |
| --- | --- |
| 普通源码 | 重启相关进程并测试 |
| 依赖／入口元数据 | 重新安装或同步环境 |
| 模型或资源清单 | 下载／校验对应资源 |
| 数据库结构 | 按项目迁移步骤升级结构并备份 |

pull 本身不会自动完成这些事情，除非项目另有明确自动化。

### 6.3 分支与双机接力

同一个人两台电脑也会有并行修改。尽量先在 A 提交推送，再到 B 拉取；需要同时工作时使用明确的功能分支，并理解最后的合并。

不要自动对有未提交内容的工作区执行破坏性重置。面对冲突，先明确保留哪些行为，再编辑合并结果、测试并提交。

### 6.4 Git 不是个人数据备份的唯一答案

大型训练数据、模型制品、数据库、用户上传内容和秘密，可能需要对象存储、制品仓库或单独备份。代码可重建不代表个人数据可重建。

Git LFS 是大型文件管理的一种方式，但有安装、额度和分发条件；不能仅为了“文件夹看起来完整”就把所有生成物塞进 Git。

## 第 7 章：构建产物、部署与迁移

### 7.1 三种交付方式

| 方式 | 接收者需要什么 | 典型场景 |
| --- | --- | --- |
| 源码与环境配方 | 对应 Python、依赖和资源 | 继续开发、研究复现 |
| wheel | 兼容 Python 与运行依赖 | 安装库或 Python 应用 |
| 独立应用／容器镜像 | 对应系统或容器运行条件 | 桌面用户、服务部署 |

wheel 不等于 Windows exe；PyInstaller 类工具的产物也不意味着跨平台。容器减少一部分系统环境差异，但仍涉及架构、宿主能力、网络、GPU 和持久数据。

### 7.2 同系统迁移步骤

以两台 Windows x64 电脑为例：

1. 确认源项目的提交、依赖清单、资源说明已保存。
2. B 安装适合项目的 Python 和 Git。
3. B 克隆源码，在自己的路径创建 .venv。
4. 按项目文档安装依赖和项目本身。
5. 配置所需环境变量、系统组件、数据与模型。
6. 运行检查、测试和一条真实用户流程。
7. 记录结果，之后按更新类型维护环境。

不要求两台绝对路径一样；要求代码没有偷偷依赖 A 的固定路径。

### 7.3 跨系统迁移多了什么

Windows 转 Linux/macOS 时额外检查：路径分隔符、大小写、文件权限、shell 命令、系统 API、原生依赖和进程模型。

一个使用 Windows 专属 OCR 的项目，即使业务代码是 Python，也不是只重建 .venv 就能在 Linux 使用。要替换平台能力或明确只支持 Windows。

“Python 可跨平台”意味着语言和生态可支持多个平台，不意味着任意项目无需修改即可跨平台。

### 7.4 离线安装需要准备的集合

在与目标兼容的平台上准备依赖 wheel、自己的 wheel、Python 安装来源、资源文件及系统组件来源。若下载集合中含源码包，还要处理构建依赖；仅缓存几个主包不够。

示意流程（先有经过核对的依赖清单）：

```powershell
python -m pip download --only-binary=:all: -r requirements.txt -d wheelhouse
python -m pip install --no-index --find-links=wheelhouse -r requirements.txt
```

这不自动包括模型、数据库、驱动或远端服务。目标平台不同，默认下载的 wheel 也可能不适合；跨平台下载需要明确目标参数并在真实目标验收。

### 7.5 部署不是只有安装

服务项目还涉及启动方式、监听地址、端口、权限、日志轮转、重启策略、数据备份和回滚；桌面项目涉及系统集成、资源路径和安装目录；自动化任务涉及计划任务账号、工作目录和失败通知。

很多“手动运行正常、定时运行失败”就是因为运行账号、环境变量和工作目录变了，而不是业务函数突然不同。

## 第 8 章：工具地图，避免过早混用

| 工具类别 | 解决的主要问题 | 初学阶段怎样看 |
| --- | --- | --- |
| venv | 项目环境隔离 | 先掌握其机制 |
| pip | Python 包安装 | 先掌握目标环境与依赖 |
| Python 版本管理器 | 安装／选择不同解释器 | 多版本项目时再引入 |
| uv、Poetry 等项目工具 | 整合环境、依赖解析与锁定等流程 | 遵守仓库已选方案，不混用锁文件 |
| Conda 类环境管理 | 管理 Python 及较多非 Python 组件 | 科学计算等场景按项目要求使用 |
| pipx 类工具 | 隔离安装独立命令行应用 | 不等于给当前项目安装依赖 |
| Docker 等容器工具 | 封装一部分运行系统环境 | 部署需求明确后学习 |
| 编辑器 | 编辑、调试和导航 | 解释器选择仍需核对 |

这些不是必须一起安装的清单。已有仓库采用某个管理方案，就先阅读它的配置与文档；不要同时用多个工具无计划地改同一个环境。

## 第 9 章：拿到陌生项目的通用阅读顺序

1. 先看 README 的用途、支持系统、运行入口和外部服务。
2. 找 pyproject.toml、requirements、锁文件、environment.yml 或容器配置，确定它采用的方案。
3. 看配置示例，分清必填设置与秘密。
4. 看 tests 和示例输入，了解预期行为。
5. 找命令入口或主程序，顺着核心流程读。
6. 在独立环境安装，先跑最小示例，再跑完整功能。
7. 记录实际 Python 路径、资源位置和验证结果。

不要拿一个生产数据库、真实邮件账号或重要目录作为陌生项目的第一份实验输入。先用项目测试数据或自己构造的小数据，理解操作的范围。

## 第二册检查题

1. 为什么源码目录可运行，不等于 wheel 可运行？
2. 应用为什么常固定环境，而给别人安装的库通常要表达兼容范围？
3. requirements 中列出一个包，与 constraints 中列出同一个包，有什么区别？
4. requirements 完全一致，还可能有哪些环境差异？
5. 为什么更新依赖的提交不能只 pull 后继续运行旧进程？
6. 若程序只在当前编辑器中正常，换目录就失败，应优先检查什么？

答案见[第三册](03-labs-and-troubleshooting.md)。这套思考方式比记住某个框架的安装命令更能复用。
